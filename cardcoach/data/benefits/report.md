### 0단계 양식에서 늘린 필드 (기존 필드는 그대로)

| 필드 | 위치 | 이유 |
|---|---|---|
| `reward_type` | 혜택 | 할인 / 캐시백 / 포인트 / 마일리지. 같은 10%라도 청구할인과 포인트 적립은 체감이 달라서 |
| `min_prev_spend` | 혜택 | 카드 안에서도 혜택마다 전월실적 조건이 다름(예: 기본 1%는 무실적, 특별 5%는 50만원). `null`이면 카드 `tiers`를 따름 |
| `limit_groups` | 카드 | 영역별 월 한도. `tiers[i]`와 같은 순서로 `limits[i]`. 혜택의 `shared_limit_group` 이름과 일치 |
| `other_services_raw` | 카드 | 라운지·바우처·무이자할부처럼 결제 할인이 아닌 서비스(분석 제외, 기록만) |
| `rate_by_tier` / `rate_by_amount` | 혜택(일부) | 실적 구간별 적립률(신한 Hi-Point), 건당 금액별 할인율(롯데 Las Vegas, IBK포인트, BC MACAO) |

`target_raw`는 카드고릴라 원문 문구를 그대로 옮기되, 앞에 `[영역명]`(예: [TIME], [SELECT 2-A])을 붙이고 긴 대상 목록은 원문 순서대로 줄여 적었다. 업종 판단은 하지 않았다(분류는 taxonomy·mapping에서).

`tiers[].monthly_limit`은 카드 전체 월 한도다(영역 한도가 있으면 그 합). 무실적 혜택이 있는 카드는 `min_prev_spend: 0` 구간이 첫 줄에 있다.

## 4. 애매했던 분류와 판단

1. **대형마트 / 창고형 / 기업형 슈퍼(SSM)를 셋으로 나눔**: 카드마다 포함·제외가 다르다. 신한 Discount Plan+·우리 7CORE는 트레이더스만 넣고 그 외 창고형과 SSM은 제외, 신한 Mr.Life는 SSM(기업형 슈퍼마켓) 포함, 삼성 CASHBACK 체크는 코스트코·에브리데이까지 포함. 하나로 묶으면 "이마트 에브리데이에서 할인됨"을 잘못 안내하게 된다.
2. **음식점 vs 패스트푸드 분리**: KB 굿데이는 음식점 할인에서 패스트푸드를 명시 제외, 신한 Discount Plan+·처음은 포함, KB My WE:SH는 목록에 없음. 버거킹 결제가 "음식점"으로 잡히는지는 카드사 업종 등록에 달려 있어 별도 코드로 둠.
3. **커피: 지정 브랜드 vs 커피전문점 업종 전체**: 같은 `FD-CAFE`지만 TEN·신한은 6개 브랜드만, KB·신한 처음·NH트래블리는 업종 전체. 업종코드만으로 추천하면 동네 카페에서 TEN을 잘못 추천하므로, 혜택의 `target_kind`(brands/category)를 같이 봐야 함.
4. **올리브영 / 다이소 분리**: 카드 원문은 "잡화: 올리브영, 다이소"처럼 묶지만, 한쪽만 있는 카드도 있다(KB 관리에 진심은 올리브영만, 삼성 SELECT ALL은 다이소만). 표준 분류도 화장품 소매 vs 생활용품으로 다르다.
5. **병원 / 약국 / 동물병원 분리**: "병원/약국"으로 묶여도 동물병원 포함 여부가 엇갈림(신한 Mr.Life·K-패스 제외, 우리 7CORE·삼성 SELECT 포함). KB 굿데이처럼 약국만 있는 카드도 있음.
6. **주유 / LPG / 전기차 충전 분리**: LPG는 여러 카드가 제외(신한 Discount Plan+·Mr.Life, 우리 SHOPPING+), 현대 알파벳O·하나 JADE·우리 OPUS blue·삼성 iD GLOBAL 등은 포함. 전기차 충전은 별도 혜택(하나 JADE Prime 30%)이 있음.
7. **골프장 vs 골프연습장**: 우리 the OPUS silver는 골프장 업종만(연습장·스크린 제외), OPUS blue는 둘 다. 연습장은 스포츠시설(`LS-SPORTS`)로, 골프장은 `LS-GOLF`.
8. **"노브랜드" 동음이의**: 이마트 PL 매장(기업형 슈퍼)인데 카카오맵에서 "노브랜드"로 찾으면 노브랜드버거(패스트푸드)가 먼저 나온다. 매핑에서 별칭을 "노브랜드"로만 두면 오인식 위험 → 별칭 매칭 시 "버거" 포함 여부 확인 필요.
9. **베이커리 카페(아티제·카페노티드)**: 아티제는 카드사(삼성 taptap O)가 커피전문점 목록에 넣어 `FD-CAFE`, 카페노티드는 하나 원더카드가 베이커리 목록에 넣어 `FD-BAKERY`. 카드 원문 기준을 따름.
10. **배달앱·온라인몰은 브랜드지만 매장 아님**: `target_kind`는 원문대로 brands로 두고, 업종코드에서 `store_recognizable: false`(ON-*)로 구분.
11. **택시·대중교통**: 카드 단말로 결제하지만 가게 사진과 무관해 혜택은 non_store로 기록. 원문이 "택시 업종"처럼 업종으로 쓰인 2건만 `TR-TAXI` 코드 부여.
12. **군마트(PX)**: "군마트"의 "마트"가 대형마트로 잡히지 않게 `RT-PX`로 분리(일반인 이용 불가).
13. **코드 미부여 2건**: 신한 SOL트립앤J "일본 돈키호테"(해외 매장), 우리 EVERY CHECK "4대 일상영역"(대상 영역 표가 이미지라 원문 없음).
14. **브랜드 미상 1건**: BC 페이북 머니 체크 "더 세임(the SameE)"은 업종을 확인하지 못해 코드 없이 둠.

## 6. 무작위 10장 재확인

`random.seed(20261027)`로 고른 10장의 상세 API를 다시 불러, 아래 항목이 원문에 그대로 있는지 자동 대조했다.

- 연회비
- 전월실적
- 각 혜택의 할인율·정액
- 대상 브랜드(최대 4개)
- 월 한도

## 7. 다음 단계(DB 연결 때 참고)

- `mapping.json`의 `benefit_codes`: 혜택 ID → 업종코드 목록. Brand/BenefitRule 테이블로 옮길 때 이걸 쓰면 원문을 다시 분류할 필요가 없다.
- `mapping.json`의 `seed_category_to_code`: seed.py의 "카페·편의점·패스트푸드…" → 새 코드 대응표.
- 엔진에 필요한데 지금 모델에 없는 것
  - 영역별 한도(`limit_groups`)
  - 일·월 횟수(`monthly_count`)
  - 혜택별 전월실적(`min_prev_spend`)
  - 요일(`days`)
  - 건당 금액별 할인율(`rate_by_amount`)
- 카카오 `category_name` 세그먼트
  - 일부는 카카오맵 검색 결과로 확인했다(`kakao_observed`).
  - 나머지는 추정이라, 실제 API 키로 한 번 더 확인해야 한다.
